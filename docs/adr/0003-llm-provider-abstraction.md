# Replace the Claude CLI with a Pluggable LLM Provider

## Status

Accepted

## Context and Problem Statement

Every summary was generated by shelling out to the `claude` CLI: the analysis stage
piped the rendered prompt into `claude --print` on stdin and read the summary back
off stdout. The only configuration was `tools.claude`, a path to the binary.

That single call site created several problems:

- **A hard dependency on one vendor's local CLI.** Contributors had to install and
  authenticate Claude Code before they could process a single meeting, and
  self-hosters could not point the tool at a model they already run or a gateway
  they already pay for.
- **No control over the request.** Model, token budget, timeout, and retry
  behaviour were whatever the CLI defaulted to. There was no way to route a body
  with unusually long meetings to a larger-context model.
- **An untestable prompt.** `MockCommander.ExecuteWithStdin` discards its stdin
  argument, so no test could assert on what was actually sent to the model. The
  prompt-building tests could only verify that the binary had been invoked.
- **Wasted work on unrecoverable failures.** `retry.Do` wraps an entire meeting,
  so a bad credential re-downloaded and re-transcribed the video on every attempt.

## Decision Drivers

- Users MUST be able to choose their own provider, model, and endpoint through
  configuration alone.
- Adding a government body MUST remain a YAML block plus a prompt template, with
  no code changes.
- API keys MUST NOT be stored in the configuration file.
- `go test ./...` MUST keep passing with no external binaries and no credentials.
- Commands that never call a model — `bodies list`, `quarantine list` — MUST keep
  working without credentials.
- The prompt sent to the model SHOULD be assertable in tests.

## Considered Options

1. Two HTTP clients behind an interface, using the official provider SDKs
2. Two HTTP clients behind an interface, hand-rolled on `net/http`
3. Keep the `claude` CLI as one provider alongside the HTTP clients
4. Adopt a third-party multi-provider abstraction library

### Option 1: Official SDKs behind an interface (chosen)

An `internal/llm` package defines a `Client` interface with two implementations:
one for the Anthropic Messages API (`POST /v1/messages`) and one for the OpenAI
Chat Completions API (`POST /v1/chat/completions`). Each wraps the vendor's
official Go SDK — `anthropics/anthropic-sdk-go` and `openai/openai-go`.

Both SDKs expose `option.WithBaseURL`, which is what makes two implementations
cover far more than two services: any endpoint speaking either protocol works,
including OpenRouter, Groq, Together, Azure OpenAI, Ollama, vLLM, and LM Studio.
The same option is what makes the clients testable against `httptest.Server`.

### Option 2: Hand-rolled on `net/http`

Attractive for a project whose dependencies are otherwise `cobra`, `viper`,
`testify`, and the standard library. Rejected because the request and response
shapes, streaming SSE framing, retry semantics, and error envelopes are all
non-trivial and change over time; the SDKs track those upstream for free.

### Option 3: Keep the CLI as a third provider

Would preserve backwards compatibility and let users with a Claude Code
subscription avoid per-token API costs. Rejected to keep one code path: the CLI
provider would need its own error mapping, could not honour `max_tokens`,
`base_url`, or `timeout`, and would keep `os/exec` in the analysis path.

### Option 4: A multi-provider abstraction library

Rejected as a dependency far larger than the two protocols actually needed, and
one that would put a third party between this project and provider behaviour.

## Decision Outcome

Chosen option: **Option 1**, official SDKs behind an `internal/llm.Client`
interface, with the `claude` CLI removed entirely.

Supporting decisions:

- **`domain.LLMConfig` owns the configuration shape**, so `internal/config` and
  `internal/llm` do not depend on each other and `domain` still imports nothing
  from the project.
- **Per-body overrides use `domain.LLMOverride`**, whose fields are pointers so
  that an omitted key inherits the global value while an explicitly zero key —
  an empty `base_url`, `stream: false` — is still honoured.
- **API keys are read from the environment at client construction**, via the
  variable named by `llm.api_key_env`. Deliberately not validated during config
  loading, so credential-free commands keep working.
- **`temperature` is a `*float64`, unset by default.** Current Claude models
  (Opus 5, Sonnet 5, Opus 4.8/4.7) reject sampling parameters with HTTP 400, so
  sending a default would break the default configuration.
- **Requests stream and are accumulated client-side.** Summaries run past 1000
  words, so `max_tokens` must be generous, and a non-streaming request that large
  risks an HTTP timeout. A `stream: false` escape hatch covers compatible servers
  with unreliable SSE.
- **Errors are classified into `llm.Kind` values.** Authentication, unknown
  model, context-window-exceeded, and invalid-request report
  `Permanent() == true`; `retry.Do` checks that via a locally declared interface
  and fails fast instead of re-transcribing the video.

This is a breaking configuration change: `tools.claude` is removed, an `llm`
block replaces it, and an API key must be exported. `README.md` documents the
upgrade.

## Consequences

### Good

- Any Anthropic- or OpenAI-compatible endpoint is reachable through configuration
  alone, including locally hosted models.
- Model, token budget, timeout, retries, and streaming are all configurable, per
  run or per body.
- The rendered prompt is finally assertable: tests drive the service through a
  stub `llm.Client` and the clients through `httptest.Server`, so prompt content,
  request shape, and error classification are all covered without credentials.
- Unrecoverable failures no longer burn three transcriptions.
- The analysis stage no longer uses `os/exec`, so `Commander` is now only for the
  two tools that genuinely are external binaries.

### Bad

- Two substantial new dependencies, each pulling its own transitive set.
- A breaking change for existing users, who must add an `llm` block and export an
  API key. A Claude Code subscription no longer suffices; API access is billed
  separately.
- "OpenAI-compatible" is a convention, not a specification. Compatible servers
  differ in details — the `max_tokens` versus `max_completion_tokens` field being
  the clearest example — so `llm.max_tokens_field` exists purely to paper over
  that, and other gaps may surface.
- Users of a local model now own its quality: the validation stage rejects
  summaries that miss required sections or word counts, which a small model may
  fail more often.
